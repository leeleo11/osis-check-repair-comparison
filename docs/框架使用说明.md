# 验算修复线实验使用说明

比较 T1–T6 能否定位并修复同一处验算失败。题面只有目标验算项。种错做法、原因码真值和 NG 清单不进模型输入。六个架构用同一份去掉 `templates/` 的技能快照和同一份候选工程。环境用 `uv`，不要提交 `.venv` 或 `.venvs`。

```powershell
$env:OSIS_PARENT_REPO = "C:\path\to\osis-skill-enhance-main"
$env:OSIS_MODEL_API_KEY = "<key>"
$env:OSIS_MODEL_BASE_URL = "http://<gateway>/v1"
uv sync --python 3.13 --extra test
uv run python scripts/setup_framework_envs.py
uv run python scripts/create_skill_snapshot.py --parent-repo $env:OSIS_PARENT_REPO
```

快照会丢掉所有名为 `templates` 的目录。模板是种错前的正确工程，留着就能对照出改动。正式运行时 runner 还会再过滤一次，写成该次 run 的 `public_skills`。

另备一个专用 OSIS scratch 工程，以及带 `pyosis` 的 Python。不要指向正在人工使用的工程。

## 怎么开跑

先不调模型，只核对题单：

```powershell
uv run python scripts/run_dataset.py `
  --parent-repo $env:OSIS_PARENT_REPO `
  --architecture T2 `
  --skills-dir tmp\check-repair-skill-snapshot `
  --dry-run
```

一条正式任务。`--architecture` 换成 T1–T6 中的一个。不写 `--model` 时，脚本默认仍是过期的 `deepseek-v4.1-flash-expires-on-0910`。和建模线对齐时写成 `deepseek-flash`：

```powershell
uv run python scripts/run_dataset.py `
  --parent-repo $env:OSIS_PARENT_REPO `
  --architecture T2 `
  --skills-dir tmp\check-repair-skill-snapshot `
  --osis-project C:\path\to\scratch-project `
  --osis-model-python C:\path\to\python.exe `
  --model deepseek-flash `
  --label formal-v1 `
  --seed 0
```

六架构一起跑：

```powershell
uv run python scripts/run_campaign.py `
  --parent-repo $env:OSIS_PARENT_REPO `
  --architectures T1 T2 T3 T4 T5 T6 `
  --skills-dir tmp\check-repair-skill-snapshot `
  --osis-project C:\path\to\scratch-project `
  --osis-model-python C:\path\to\python.exe `
  --model deepseek-flash `
  --label formal-v1 `
  --seed 0 `
  --jobs 2 `
  --resume
```

跑完后由统一 runner 把候选 `py/` 拷进 scratch，执行 `main.py`、`solve`，再验算。定位分看最后一个 `reason_code` 是否等于隐藏真值。修复分看目标项是否通过，且没有新增 NG。

## 并行还是串行

`--jobs` 只作用于 T1–T5，默认 1。这些架构的生成可以并行。正式验算都要打到本机 OSIS（端口 18080），求解阶段不要和建模线的求解重叠。

T6 独占隔离 OpenCode 和 OSIS，campaign 始终把它放在串行队列，`--jobs` 对它无效。不要同时开两个 T6。

`--resume` 跳过已经完成的 run。结果在 `runs/<label>/`，不进 Git。汇总方法见 [实验数据后处理.md](实验数据后处理.md)。

## 六个架构怎么接工具

技能快照相同，都去掉了 `templates/`。工具不是同一套。正式验算不放进任何框架的工具列表：适配器交卷后，统一 runner 把候选 `py/` 拷进 scratch，跑 `main.py`、`solve`，再验算。定位和修复分只看这一次结果。

驱动按架构选解释器。T1、T2 用仓库 `.venv`，T3–T5 用 `.venvs/t3`、`t4`、`t5`。T6 用父仓库的 OpenCode 和带 `pyosis` 的 Python。

| 架构 | 动作 | 技能怎么给 | 候选工程怎么改 |
| --- | --- | --- | --- |
| T1 | 一次请求，没有工具循环 | 技能正文和当前候选文本放进提示词 | 回复中的 `### FILE:` 块，路径必须落在候选工程内 |
| T2 | LangGraph `create_agent` | `list_skills`、`read_skill`、`read_skill_reference`、`list_reference_files`、`search_skill_cases` | `list_candidate_files`、`read_candidate_file`、`write_candidate_file` |
| T3 | smolagents `CodeAgent`，`tools=[]` | 解释器放行 `json`、`pathlib`，用 `pathlib` 读快照 | 用 `pathlib` 改候选文件。不放行 `pyosis` |
| T4 | OpenHands 默认智能体 | `load_skills_from_dir`，先 `invoke_skill` | 官方 `terminal`、`file_editor`、`task_tracker`。浏览器关闭。工作目录是候选工程 |
| T5 | CrewAI：诊断、修复、复核 | `Crew(skills=...)` 的 `load_skill`。它只返回 `SKILL.md`，同一次 `kickoff` 里用 `read_skill_resource` 读快照里的其余文件 | 诊断和复核用 `DirectoryReadTool`、`FileReadTool`。修复者另有 `FileWriterTool`，目录限制在候选工程。`allow_delegation=True`。代码执行关闭 |
| T6 | 父仓库 OSIS-AI 一次会话 | 只挂本 run 的无模板快照，不挂父仓库原始 `.agents/skills` | 会话自己的文件和命令工具。交卷后仍由本仓库 runner 重建、求解、验算 |

## 为什么各框架能力不同

比较的是各框架自己的动作接口。实验不另做一套人人都能调用的「跑验算」工具。某个框架的官方接口里没有执行器，就不给它补一个。交卷后的 `main.py`、求解和验算是评分，不是送回同一次运行的报错。

- T1 没有工具循环。技能和当前候选一次放进提示词。
- T2 的 `create_agent` 不自带工具。调用方交给它的是读技能和读写候选文件。`search_skill_cases` 只搜这份无模板快照。库本身没有验算动作，所以不加。
- T3 的动作是 Python 解释器，`tools=[]`。允许导入只有 `json` 和 `pathlib`，用来读快照、改候选。这里不放行 `pyosis`：正式验算由 runner 在交卷后执行。若把 `pyosis` 放进解释器，T3 就能在同一次运行里看到验算结果，T2 和 T5 看不到。这和建模线不同。建模线的 T3 要写出并可以调用建模库，验算线的交付物是改好的候选源码。
- T4 有官方终端和文件编辑器。终端是它自己的执行器。实验没有往 `.venvs/t4` 里装 `pyosis`，也没有把验算器注册成额外工具。
- T5 在同一次 `kickoff` 里诊断、改文件、复核。CrewAI 1.15 的代码解释器已废弃，`allow_code_execution=True` 不会注册工具，所以保持关闭。`read_skill_resource` 只补 `load_skill` 读不到的同一份快照，不是验算工具。
- T6 用父仓库 OSIS-AI 的指令和它自己的命令工具，会话里可以按技能去调 PyOSIS。那是这条框架自己的循环。本仓库的 runner 不把验算报错再贴回会话。评测阶段没有语法硬门禁：`main.py` 跑不起来会在重建时失败，与父仓库 `--rebuild` 一致。

T1–T5 在进入 OSIS 之前有语法编译门禁。编译失败的候选不会当成修复成功。
